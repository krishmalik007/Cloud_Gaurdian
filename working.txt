================================================================================
                    CLOUDGUARDIAN - COMPLETE ARCHITECTURE & WORKING
================================================================================

CloudGuardian is a next-generation Multi-Cloud Security Operations Center (SOC) 
and Security Information and Event Management (SIEM) platform designed for 
hybrid and multi-cloud environments (AWS, Azure, and GCP).

Its core mission is to collect cloud security logs in real-time (via SQS/EventBridge) 
or on-demand (via manual upload & API ingestion), normalize diverse vendor schemas 
into a unified standard format, evaluate events against a stateful correlation 
engine and threat intelligence database, dynamically calculate risk scores, 
generate actionable security incidents, and broadcast live alerts to a modern 
interactive security dashboard over WebSockets.

================================================================================
1. FULL TECH STACK & SYSTEM ARCHITECTURE
================================================================================

CloudGuardian is built on a decoupled, asynchronous, enterprise-grade architecture
consisting of four primary pillars:

--------------------------------------------------------------------------------
A. CONTAINERIZED INFRASTRUCTURE (Docker Compose)
--------------------------------------------------------------------------------

• Apache Kafka (v3.9.1 - KRaft Mode) (Port 9092):
  - High-throughput, distributed event streaming platform.
  - Runs in ZooKeeper-less KRaft mode for optimal performance.
  - Automatically initializes the primary 'cloud_logs' topic via an automated 
    `kafka-setup` helper container.
  - Decouples log ingestion from backend analysis, ensuring zero log loss during 
    high-volume traffic spikes.

• OpenSearch (v2.11.1 - Secured Cluster) (Port 9200):
  - Distributed search and analytics engine with TLS/HTTPS encryption enabled.
  - Secured with dedicated node and root CA x509 certificates generated via 
    custom certificate tooling (`generate_certs.py`).
  - Serves as the primary datastore for:
    * Users & Credentials (`users` index)
    * Active User Sessions & Online Presence (`sessions` index)
    * Security Incidents & Alerts (`incidents` index)
    * Indicators of Compromise / Threat Intel (`iocs` index)
    * System Audit Trails & Activity Logs (`audit_logs` index)

--------------------------------------------------------------------------------
B. BACKEND API & EVENT PROCESSING (FastAPI + Python 3.10+)
--------------------------------------------------------------------------------

• Web Framework: FastAPI with Uvicorn ASGI server.
• Data Validation & Config: Pydantic v2 & Pydantic-Settings with strict 
  environment variable validation and cached singleton access.
• Real-Time Cloud Ingestion: Boto3-powered AWS SQS Consumer (`AWSSQSConsumer`) 
  with long-polling (20s) and automatic visibility timeout retries.
• Message Streaming: `confluent-kafka` for high-speed Kafka producing & consuming.
• Search & Storage Client: `opensearch-py` with SSL/TLS verification.
• Authentication & Security: 
  - PyJWT for Access Token (30m) and Refresh Token (7d) rotation.
  - Passlib & Bcrypt for salted password hashing.
  - Slowapi rate limiting (e.g. 5 req/min on login/register endpoints).
  - SecurityHeadersMiddleware (X-Content-Type-Options, X-Frame-Options, Referrer-Policy).
  - Sensitive data redaction utility for masking tokens, passwords, and secrets.
• Real-Time Communication: FastAPI WebSockets (`/ws/dashboard`) managed by 
  `WebSocketManager` with token authentication and role validation.

--------------------------------------------------------------------------------
C. FRONTEND CLIENT (React 18 + Vite + Tailwind CSS)
--------------------------------------------------------------------------------

• Framework: React 18 SPA built with Vite.
• Routing: React Router v6 with granular Role-Based Access Control (`ProtectedRoute`).
• Server State & Caching: TanStack React Query v5 for automatic data caching, 
  background refetching, and query invalidation.
• Styling & Animation: Tailwind CSS, custom design tokens, dark/light ThemeContext, 
  Lucide React icons, and Framer Motion micro-animations.
• Data Visualization: Chart.js and `react-chartjs-2` for security metrics, incident 
  trends, severity distributions, and cloud provider breakdowns.
• Forms & Notifications: React Hook Form, Zod schema validation, and React Toastify.
• Error Handling: React ErrorBoundary catching render exceptions and dedicated 
  HTTP error pages (401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Server Error).

2. STEP-BY-STEP LOG INGESTION & PIPELINE FLOW
================================================================================

CloudGuardian supports two parallel ingestion paths: Real-time Cloud Streaming 
and Direct API / Batch Upload. Both feed into the same core processing pipeline:

   [AWS CloudTrail / EventBridge]              [Manual UI Upload / REST API]

                │                                             │
                └──────────────► [Kafka 'cloud_logs'] ◄───────┘
                                        │
                                        ▼
                            [KafkaConsumer / LogProcessor]
                                        │
                                        ▼
                         [Step 1: Sensitive Data Redaction]
                                        │

                         [Step 2: Cloud Provider Detection]
                                        │
                                        ▼
                         [Step 3: Schema Normalization]
                                        │

          (Searchable Data Store)             (Live Dashboard Update)

--------------------------------------------------------------------------------
DETAILED PIPELINE BREAKDOWN
--------------------------------------------------------------------------------

1. INGESTION & REDACTION:
   - AWS EventBridge captures CloudTrail API calls and routes them to an AWS SQS queue.
   - `AWSSQSConsumer` polls SQS, passes raw payloads through `redact_sensitive_data()`, 
     and publishes them to the Kafka `cloud_logs` topic.
   - Alternatively, analysts can upload raw JSON logs directly via the Web UI.

2. CLOUD PROVIDER DETECTION:
   - Detects log format by inspecting vendor signatures (AWS CloudTrail, Azure Activity, 
     Azure AD/Entra ID Sign-ins, GCP Cloud Audit Logs).

3. SCHEMA NORMALIZATION (`app/normalizer/`):
   - Translates vendor-specific fields into the canonical `NormalizedLog` schema:
     { provider, event_name, event_type, source_ip, username, event_time, 
       region, domain, raw_log, user_agent, error_code, status }
   - Normalizes disparate action names (e.g. AWS 'ConsoleLogin', Azure 'SignIn', 
     GCP 'google.login') into standard types (LOGIN_SUCCESS, FAILED_LOGIN, ROOT_LOGIN, 
     CREATE_ADMIN_USER, PUBLIC_BUCKET_CREATED, AUDIT_LOGGING_DISABLED, etc.).

4. THREAT INTELLIGENCE LOOKUP (`app/threat_intelligence/`):
   - Queries OpenSearch `iocs` index for matches against Source IP, Domain, and Username.
   - Appends IOC metadata, calculates threat multiplier, and assigns tags 
     (e.g., `MALICIOUS_IP`, `MALICIOUS_DOMAIN`, `SUSPICIOUS_USERNAME`).

5. CORRELATION ENGINE (`app/correlation/`):
   - Stateful in-memory `EventStore` tracks temporal windows per IP/user.
   - Evaluates multi-event security rules:
     * Authentication: Brute force attacks, rapid failed logins, off-hours access, 
       concurrent logins from different locations.
     * IAM: Root account usage, excessive admin privilege escalation, policy tampering.
     * Resource: Public S3 buckets/blobs, open database ports (3306, 5432, 27017), 
       0.0.0.0/0 security group ingress.
     * Data: Massive file downloads, sensitive object reads (data exfiltration).
     * Configuration: CloudTrail / GuardDuty disabled, encryption deactivated.

6. RISK ENGINE (`app/risk/`):
   - Aggregates base rule scores, threat intel severity, and environmental weights.
   - Generates a normalized 0–100 Risk Score and Severity Rating:
     • 0 – 39   : LOW
     • 40 – 69  : MEDIUM
     • 70 – 89  : HIGH
     • 90 – 100 : CRITICAL

7. ALERT CREATION & REAL-TIME BROADCAST:
   - Compiles incident payload with MITRE context, remediation advice, and raw event evidence.
   - Persists incident into OpenSearch `incidents` index.
   - Pushes instantaneous JSON notification over `ws_manager` to all active WebSocket clients.

3. SECURITY, SESSIONS & USER MANAGEMENT
================================================================================

CloudGuardian incorporates a multi-tiered security and governance model:

• Role-Based Access Control (RBAC):
  - Roles: `ADMIN` and `ANALYST`.
  - ADMIN: Full access including user management, role modification, account 
    enable/disable, and system audit logs.
  - ANALYST: Access to Dashboard, Incidents, Threat Center, IOCs, and Log Ingestion.

• Session Tracking & Online Presence:
  - Every login generates a distinct `session_id` stored in OpenSearch (`sessions` index).
  - Tracks user online/offline status dynamically across the Users Management portal.
  - On user logout or session expiration, sessions are invalidated immediately.

• Audit Logging:
  - System-wide audit trail recording user logins, role changes, user status toggles, 
    IOC modifications, and incident status updates in the `audit_logs` index.

• API Rate Limiting & Hardening:
  - Slowapi protects authentication endpoints against brute force attempts.
  - Strict JWT validation checks requiring minimum 32-character high-entropy secret.
  - OWASP-recommended HTTP security headers attached to all API responses.

4. FRONTEND APPLICATION STRUCTURE
================================================================================

The React client located in `frontend/src` consists of:

• context/:
  - `AuthContext.jsx`: Authentication state, JWT token management, automatic refresh, 
    login/logout lifecycle, and active user payload.
  - `ThemeContext.jsx`: Dark / Light theme toggle with persistent localStorage.

• layouts/:
  - `DashboardLayout.jsx`: Navigation sidebar, real-time WebSocket status, notifications 
    toast container, user profile header, and breadcrumbs.
  - `AuthLayout.jsx`: Centered glassmorphic card layout for Login and Register pages.

• pages/:
  - `dashboard/Dashboard.jsx`: Live incident KPI cards, provider breakdown chart, 
    risk score breakdown, real-time activity stream, and health telemetry.
  - `incidents/IncidentPage.jsx` & `IncidentDetails.jsx`: Comprehensive incident list 
    with severity filters, search, status updating (OPEN, INVESTIGATING, RESOLVED, CLOSED), 
    analyst assignment, and deep forensic breakdown.
  - `logs/UploadLogs.jsx`: Interactive log upload interface with AWS/Azure/GCP preset 
    templates and instant schema validation.
  - `ioc/IOCManagement.jsx`: Complete IOC CRUD portal (IPs, Domains, Usernames) with 
    severity tags and enable/disable toggles.
  - `threat/ThreatCenter.jsx`: Interactive reputation search and threat analysis tool.
  - `users/Users.jsx`: Admin portal for managing analysts, switching roles, 
    enabling/disabling accounts, and viewing live online presence indicators.
  - `audit/AuditLogsPage.jsx`: Filterable audit log stream for compliance tracking.
  - `profile/Profile.jsx` & `settings/Settings.jsx`: User profile and configuration.
  - `error/`: Dedicated 401, 403, 404, and 500 status pages.

5. HOW TO RUN AND VERIFY LOCALLY
================================================================================

--------------------------------------------------------------------------------
STEP 1: Start Container Infrastructure (Docker)
--------------------------------------------------------------------------------
Launch Apache Kafka and OpenSearch with TLS encryption:

  docker compose up -d

Verify containers are running:
  docker ps

Expected active containers:
- `kafka` (Port 9092)
- `kafka-setup` (Exits 0 after creating topics)
- `opensearch` (Port 127.0.0.1:9200)

--------------------------------------------------------------------------------
STEP 2: Configure Environment Variables
--------------------------------------------------------------------------------
Ensure `backend/.env` is configured properly:

  KAFKA_BOOTSTRAP_SERVERS=localhost:9092
  KAFKA_TOPIC=cloud_logs
  OPENSEARCH_HOST=localhost
  OPENSEARCH_PORT=9200
  OPENSEARCH_USERNAME=admin
  OPENSEARCH_PASSWORD=<your_secure_password>
  OPENSEARCH_USE_SSL=true
  OPENSEARCH_VERIFY_CERTS=false
  OPENSEARCH_CA_CERTS=certs/opensearch/root-ca.pem
  JWT_SECRET_KEY=<minimum_32_character_random_hex_key>
  JWT_ALGORITHM=HS256
  JWT_EXPIRE_MINUTES=30
  JWT_REFRESH_TOKEN_EXPIRE_DAYS=7
  # Optional: For Real-Time AWS SQS Ingestion
  AWS_ACCESS_KEY_ID=<your_aws_key>
  AWS_SECRET_ACCESS_KEY=<your_aws_secret>
  AWS_REGION=ap-south-1
  AWS_SQS_QUEUE_URL=<your_sqs_queue_url>

--------------------------------------------------------------------------------
STEP 3: Start the FastAPI Backend
--------------------------------------------------------------------------------
Navigate to the backend directory and launch the server:

  cd backend
  pip install -r requirements.txt
  python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

Startup checks:
- "OpenSearch is connected and ready."
- "AWSSQSConsumer started." (if configured)
- "Kafka consumer thread started."
- "WebSocket manager loop initialized."

--------------------------------------------------------------------------------
STEP 4: Start the Vite Frontend
--------------------------------------------------------------------------------
In a separate terminal:

  cd frontend
  npm install
  npm run dev

Access the dashboard at: http://localhost:5173

--------------------------------------------------------------------------------
STEP 5: End-to-End Verification
--------------------------------------------------------------------------------
1. Open http://localhost:5173 and register a new user account.
2. Log in with the registered credentials.
3. Open "Upload Logs" and paste a sample cloud security event:
   {
     "provider": "AWS",
     "eventName": "ConsoleLogin",
     "sourceIPAddress": "198.51.100.1",
     "awsRegion": "us-east-1",
     "userIdentity": {
       "userName": "malicious_user"
     },
     "eventTime": "2026-08-24T12:00:00Z"
   }
4. Submit the log.
5. Check the "Dashboard" and "Incidents" pages — the new incident appears 
   immediately with dynamic risk score, IOC cross-references, and severity badges.
6. Check "Users" (as ADMIN) to view active sessions and online presence.
7. Verification complete — CloudGuardian is fully operational!
